# POC v3 业务指标化优化计划

本文用于指导 `prototype-v3` 下一阶段优化：不推翻现有技术路线，把当前区域质检闭环升级为更贴近业务关切的巡检质量大屏。

## 目标判断

当前 v3 已经能讲清“表单质检、时序预警、视觉证据、Agent 建议、人工确认、报告归档”的技术闭环，但首页仍偏向“区域态势”和“设备异常”。业务方更关心的是巡检质量本身：

```text
巡检有没有完成
工人有没有按要求巡检
有没有快检、漏检、异常时段巡检
AI 如何辅助人工巡检质量分析
问题是否复核、报告是否归档、经验是否沉淀
```

所以下一阶段的设计重心应从“设备异常分析 demo”转为“巡检质量智能分析 demo”。设备、区域、时序和视觉仍然保留，但它们要服务于巡检质量判断，而不是成为首页主叙事。

## 参考启发

附件4的大屏首页有几个可借鉴点：

```text
中心：业务场景 / 地图 / 三维空间
左侧：核心数量、完成情况、趋势统计
右侧：任务状态、异常分布、待处理列表
底部：告警明细、任务明细、趋势小图
点击：从指标下钻到证据、任务或报告
```

迁移到巡检 demo 时，应保留这种“业务态势 + 指标 + 明细 + 下钻”的结构，但不要照搬配网工况、电压负荷等业务内容。巡检 demo 首页应让评委第一眼看到巡检质量价值，而不是先理解 6 个区域分别是什么。

## 设计原则

这次优化不是把客户原始数据实时接入 demo，而是用客户材料建立业务语境，再在 `poc/prototype-v3` 内维护一套可演示、可替换、可追溯的数据包。

```text
业务相关：指标、页面、术语要贴近巡检质量管理。
演示自洽：数据要能支撑完整演示链路，但不承诺真实计算。
目录独立：demo 页面运行只依赖 prototype-v3 自己的数据和素材。
来源可查：参考过的原始材料只作为 source 元数据，不影响页面运行。
后续可换：客户补齐真实字段后，可以替换 demo 数据，不需要重做页面。
```

因此，附件3和附件4只作为业务理解和造数依据。凡是 demo 页面实际引用的 JSON、CSV、图片、关键帧、bbox、图谱节点和问答样例，都应放在 `poc/prototype-v3` 目录下单独维护。需要使用原始图片时，复制到 v3 对应素材目录；需要使用原始表格时，抽取或改写成演示数据，不一比一复刻业务数据。

## 数据边界

目前已有数据可以支撑基础演示，但不能支撑所有精细指标的真实计算。开发上可以先用演示数据补齐，后续再和业务方对齐真实口径。

| 数据项 | 当前支撑情况 | 处理建议 |
|---|---|---|
| 巡检任务 | `巡检任务.xlsx` 有任务、机构、计划/实际日期、执行人等字段。 | 可作为首页任务总量、完成率和时间筛选基础。 |
| 执行人员 | `任务执行人.xlsx` 有人员、岗位、单位和任务关联。 | 可做人员维度排行、班组统计。 |
| 巡检结果 | `巡检结果.xlsx` 有大量结果记录和 `data_value`。 | 可做结果数量展示；不要直接把非“正常”数值当成问题，需补演示问题口径。 |
| 巡检轨迹 | `巡检轨迹.xlsx` 有经纬度、人员、任务关联。 | 可做轨迹点/路线展示；缺秒级时间和区域映射，不能严谨计算停留时长。 |
| 巡检步骤 | `任务执行步骤.xlsx` 有步骤和任务关联。 | 可做步骤覆盖数量；缺开始时间，不能算步骤耗时。 |
| 巡检时长异常 | 需要低于 10 分钟判断。 | 当前时间粒度不足，先用演示数据补齐秒级开始/结束时间。 |
| 区域间隔异常 | 需要区域内/区域间低于 10 秒判断。 | 当前缺采样时间、点位顺序、区域映射，先用演示数据补齐。 |
| 巡检时段异常 / 无人巡检 | 需要工业电视时间窗和人员识别结果。 | 当前缺视频识别数据，先用演示数据表达 AI 能力。 |
| 时序提醒 | 电池电压下降、污油罐液位缓慢增加。 | 当前缺完整时序库、单位、阈值、设备映射，先构造趋势曲线。 |
| 视觉识别 | 正反案例图、检测框、类别、置信度。 | 当前缺完整视觉结果，先用现有关键帧和演示 bbox 补齐。 |
| 知识库 | 需要制度、案例、问答和归档管理。 | 现有材料可做初始知识库，新增前端管理和图谱展示。 |

对外表述口径：

```text
已有数据支撑基础巡检业务展示。
精细规则和模型分析数据先用演示数据补齐，不影响功能开发。
下周再对齐哪些字段来自原始数据，哪些字段后续补充或替换。
```

首页和下钻页必须给关键指标保留数据来源标记，避免用户误解所有指标都已由客户原始数据真实计算。标记分三类：

```text
客户数据：来自附件3原始数据，可直接或轻加工展示。
演示推演：为说明 AI 能力和业务流程而构造的演示数据。
待确认：需要业务方补充字段、阈值或口径后才能真实计算。
```

核心指标的数据来源矩阵：

| 首页指标 / 页面元素 | 客户已有字段 | 演示补齐字段 | 客户后续补充字段 | 页面展示口径 |
|---|---|---|---|---|
| 机构 / 时间区间 | `巡检任务.dept_name`、`actual_end_time`、`plan_start_time` | 无 | 状态码字典、统计周期口径 | 标记为“客户数据”。 |
| 巡检完成率 | `巡检任务.work_order_id`、`order_status`、`actual_start_time`、`actual_end_time` | 未完成、进行中、超期样例 | 完成状态码含义、应巡检任务分母 | 标记为“客户数据 + 待确认”。 |
| 巡检发现问题数量 | `巡检结果.data_value`、`definition_id`、`item_id` | `is_issue`、`issue_type`、`severity`、问题描述 | 问题判定字段或规则 | 标记为“演示推演”，不把非“正常”数值直接当问题。 |
| 巡检时长异常 | 任务日期字段 | 秒级 `actual_start_at`、`actual_end_at`、低于 10 分钟样例 | 秒级时间或真实工时字段 | 标记为“演示推演 / 待确认”。 |
| 区域间隔异常 | 轨迹经纬度、`work_order_id` | `sampled_at`、`area_id`、`position_order` | 区域边界、点位顺序、采样时间 | 标记为“演示推演 / 待确认”。 |
| 巡检时段异常 / 无人巡检 | 暂无直接字段 | 摄像头检测时间、人员识别结果、视频偏差样例 | 工业电视数据、摄像头区域、人员识别结果 | 标记为“演示推演”。 |
| 电池电压趋势下降 | 可从结果数值中选映射样例 | 连续曲线、单位、阈值、设备名 | 时序库字段、设备映射、采样周期 | 标记为“演示推演 / 待确认”。 |
| 污油罐液位缓慢增加 | v3 已有演示趋势基础 | 连续曲线、阈值、趋势窗口 | 真实液位时序、阈值口径 | 标记为“演示推演 / 待确认”。 |
| 轨迹主画布 | `巡检轨迹.latitude`、`longitude`、`creator_name`、`work_order_id` | 异常点、区域边界、停留提示 | 点位名称、区域边界、秒级轨迹时间 | 轨迹点标记为“客户数据”，异常解释标记为“演示推演”。 |
| 视觉识别证据 | 现有关键帧素材 | bbox、类别、置信度、正反案例 | 真实视觉模型输出 | 标记为“演示推演”。 |
| 知识库文档 | 制度、巡检材料、报告样例 | 上传状态、标签、案例关联 | 首批正式知识库范围 | 标记为“演示推演”，不表示已接入真实检索。 |

## 页面结构调整

目标页面关系：

```text
首页业务大屏
  -> 任务质量明细
  -> 巡检轨迹与打卡详情
  -> 区域/任务详情页
       表单质检
       时序模型详情
       视觉模型详情
       Agent 辅助复检建议
       人工确认
       报告归档
  -> 知识库管理
  -> 知识节点关系图
```

首页负责回答“巡检质量整体怎么样”；详情页负责回答“某个异常为什么需要复核”；知识库和关系图负责回答“本次复核如何沉淀为经验”。三类页面不要抢同一个叙事位置。

### 1. 新首页：巡检质量指标大屏

首页从“站场区域总览”调整为“巡检质量态势总览”。

建议一屏结构：

```text
顶部
  机构选择 / 时间区间 / 任务批次 / 数据来源标记

左侧
  巡检完成率
  巡检发现问题数量
  巡检时长异常次数
  巡检时间间隔异常次数
  巡检时段异常次数

中间
  巡检轨迹/站场态势主画布
  轨迹点、异常点、视频核验点叠加显示

右侧
  AI 智能分析异常提醒
  电池电压趋势下降
  污油罐液位缓慢增加
  待人工复核任务

底部
  异常明细列表
  人员/班组质量排行
  最近归档案例
```

每张指标卡、每条 AI 提醒和每个下钻详情都要显示数据来源标记：

```text
客户数据
演示推演
待业务确认
```

不要只在顶部放一个全局说明，否则用户容易误解首页所有指标都已经由原始数据真实计算。

首页点击路径：

```text
完成率 / 异常次数
  -> 任务质量明细

轨迹异常点
  -> 轨迹与打卡详情

AI 提醒
  -> 时序/视觉/Agent 证据详情

归档案例
  -> 知识库案例详情
```

### 2. 现有区域页：保留为详情能力

当前 v3 的区域、表单、时序、视觉、Agent、复检、报告能力不删除，而是调整定位：

```text
旧定位：主页核心主线
新定位：首页下钻后的区域/任务详情页
```

也就是说，现有“计量区差压异常”仍可作为一条主线案例，但它不再是首页唯一重点，而是业务大屏中某个 AI 提醒或待复核任务的下钻详情。

### 3. 新增知识库管理页

新增“知识库管理”子页面，作为报告归档后的扩展展示，不放在首页主线之前。它的作用是体现业务可运营和经验沉淀：

```text
知识库文档列表
  巡检制度
  交接班记录
  历史质检报告
  典型异常处置案例

上传入口
  上传制度文档
  上传巡检记录
  上传复检报告

归档入口
  本次报告归档为案例
  生成标签
  绑定设备、区域、异常类型、规则依据
```

首版只做前端演示，不接真实文件服务；上传可以展示“已加入知识库”的演示状态。

硬约束：首版只演示前端状态，不代表已接入真实上传、文档解析、向量检索或问答增强链路。

### 4. 新增知识节点关系页

新增“知识图谱/知识关系”展示页，作为答辩加分页和归档后的扩展展示，不替代巡检质量主线。不需要真实图数据库，只做前端可视化效果。

建议节点类型：

```text
制度条款
巡检任务
巡检项
异常规则
时序指标
视觉证据
复检报告
归档案例
Agent 问答
```

展示关系：

```text
巡检项 -> 命中规则
命中规则 -> 证据
证据 -> 复检建议
复检建议 -> 人工结论
人工结论 -> 报告归档
报告归档 -> 相似案例
相似案例 -> Agent 问答增强
```

这个页面的价值是让评委看到“AI 不是一次性回答，而是在沉淀巡检经验”。

硬约束：首版只演示节点关系效果，不代表已接入真实图谱存储、图查询或自动知识抽取。

## 演示主线建议

下一版演示可以按 6 步讲：

```text
1. 首页看巡检质量态势
   完成率、问题数、时长异常、间隔异常、时段异常、AI 提醒。

2. 点击异常任务
   进入某次巡检，查看人员、路线、表单、轨迹和异常原因。

3. 查看 AI 证据
   并联展示时序趋势、视觉关键帧、表单记录冲突。

4. Agent 给出复检建议
   综合规则、证据和知识库，提示人工复核重点。

5. 人工确认并生成报告
   强调 AI 辅助，人工仍是最终确认主体。

6. 报告归档到知识库
   新案例进入知识库，并在关系图中体现与规则、证据、问答的关联。
```

## 数据构造计划

首版不等待客户补齐所有数据，先按如下层次构造：

| 层级 | 数据来源 | 用途 |
|---|---|---|
| 原始参考层 | 附件3/附件4 | 只用于理解业务、字段、指标和页面风格，不作为运行时依赖。 |
| demo 基础层 | v3 本地 JSON/CSV | 任务、人员、结果数量、轨迹点、机构和时间筛选。 |
| 演示补齐层 | v3 本地 JSON/CSV | 秒级时间、区域停留、区域间隔、时段偏差、问题标签。 |
| 模型演示层 | v3 本地 JSON/图片 | 时序趋势、视觉识别框、置信度、AI 提醒、关键帧。 |
| 知识库层 | v3 本地 JSON/复制素材 | 知识库列表、Agent 问答、案例归档、节点关系。 |

运行时原则：

```text
index.html 不直接读取 assets/data。
scripts/data.js 不直接引用 assets/data。
页面图片、图表数据、知识库样例都从 poc/prototype-v3 内加载。
sourceHint 可以记录参考来源，但不能成为页面运行依赖。
```

建议后续新增数据包，不直接污染现有区域数据：

```text
poc/prototype-v3/data/dashboard/
  quality-metrics.json
  task-quality-list.json
  worker-quality-ranking.json
  route-anomalies.json
  ai-alerts.json

poc/prototype-v3/data/knowledge/
  documents.json
  cases.json
  graph.json
  qa-examples.json

poc/prototype-v3/assets/
  dashboard/
  evidence/
  knowledge/
```

新增 `dashboard` 和 `knowledge` 数据仍复用现有构建链路：

```text
poc/prototype-v3/data/*
  -> tools/build-data.py
  -> scripts/data.js
  -> index.html
```

不新增后端服务，不新增运行时数据通道。

## 实施阶段

### P0：先完成可演示主线

- 首页业务大屏重构。
- 核心指标卡和数据来源标记。
- 轨迹/异常点主画布。
- 首页下钻到现有区域/任务详情。
- 本地 demo 数据包独立运行。
- 页面文案避免暗示真实实时接入。

### P1：再增强知识沉淀表达

- 知识库管理页。
- 知识节点关系图。
- 报告归档和知识库案例的前端状态联动。
- Agent 问答中展示“相似案例提供上下文”，但不声称真实向量检索。

### 阶段一：首页业务化

- 重构首页为巡检质量大屏。
- 引入核心指标：完成率、发现问题数、时长异常、间隔异常、时段异常、AI 提醒。
- 保留中间主画布，但从“6 区域说明”调整为“巡检轨迹/异常点/任务态势”。
- 首页入口指向现有表单质检详情。

### 阶段二：数据口径补齐

- 从附件3抽取可用基础统计。
- 构造演示数据补齐精确时间、区域映射、时序曲线、视觉识别。
- 在页面中标注或内部维护数据来源，区分原始数据和演示数据。

### 阶段三：知识库管理

- 新增知识库文档列表、上传入口、案例归档状态。
- 将报告归档从“单次结束动作”升级为“知识沉淀动作”。
- 定位为归档后的扩展展示，不抢首页和任务详情主线。

### 阶段四：知识节点关系

- 新增前端图谱页。
- 用节点和连线展示制度、任务、异常、证据、报告、案例、问答之间的关系。
- 不接真实图数据库，首版只做静态演示数据和交互效果。
- 定位为答辩加分页，服务“知识沉淀”表达，不作为核心操作入口。

### 阶段五：演示串联与截图验证

- 打通首页指标到区域详情、知识库、图谱的跳转。
- 用 Playwright 截图验证首页、详情、知识库、图谱一屏效果。
- 确认页面文案不夸大数据来源。

## 不做的事

- 不接真实后端服务。
- 不接真实图数据库。
- 不声称当前客户数据已经包含全部模型分析字段。
- 不把非“正常”的数值读数直接包装成真实问题数量。
- 不等待客户补齐全部数据后才开发页面。

## 下周对齐问题

需要和业务方确认：

1. `WorkOrderStatus02` 等状态码的业务含义。
2. 巡检完成率的分母：计划任务、应巡任务，还是已下发任务。
3. “发现问题数量”的真实判定字段或规则。
4. 巡检时长异常是否以任务、区域还是点位为单位。
5. 区域间隔异常需要哪些区域边界和点位顺序。
6. 工业电视是否能提供人员识别、摄像头区域和时间窗数据。
7. 电池电压、污油罐液位等时序指标的设备、单位、阈值和采样周期。
8. 知识库首批文档范围：制度、报告、交接班记录、历史案例分别提供哪些。

## 验收标准

下一版 demo 至少要让业务方和评委一眼看明白：

```text
AI 不只是判断设备有没有异常，
还在辅助管理人工巡检质量：
看任务、看人员、看轨迹、看时长、看视频、看异常、看复核、看沉淀。
```

并且要能清楚区分：

```text
哪些来自客户已有巡检数据
哪些是为了演示 AI 能力临时构造的数据
哪些需要客户后续补充或替换
```
