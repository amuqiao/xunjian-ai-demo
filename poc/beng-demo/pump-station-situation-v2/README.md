# pump-station-situation-v2 · 长岭站 P-1 输油泵机组状态（泵课题次屏）

`pump-station-situation` 的重做。骨架照 `poc/inspection-demo/inspection-station-v2` 搬，
数据换成一台输油泵机组。旧目录未删、仍可独立运行。

## 一、为什么重做：旧屏是四屏挤在一屏里

旧目录 15618 行，一屏里塞了 6 步流程轨、诊断工作台、时序/视觉整屏子屏、知识库、
Agent 问答、归档确认。**那些是诊断台那一屏的事**（`poc/beng-demo/diagnosis-flow`）。

本屏收窄成一个问题：

> **这台机组现在什么状态、哪个测点最差。**

于是屏上只剩：4 个大数 / 2 张图 / 1 张机组档案 / 1 张测点明细表 / 6 张部位卡。

## 二、第二维是「测点」，不是时间

大屏 `hunan-pump-overview-v2` 是 40 台机组的横截面（一个时点）。按 `inspection-station-v2`
的路子，次屏本该配时间。但真实资料只有两个时点 —— 2025-04-08 现场检测、2026-06-30 在线
监测月报，**两点连不成趋势**，编一条 14 轮的时间序列就是假的。

所以第二维取**空间**：25 个标准测点在机组上的分布。

## 四、25 个测点怎么挂到 3D 的 6 个部位上

3D 层（`../pump-station-situation/scripts/pump3d/`）的部位 id 空间是固定的 6 个，
`Pump3DContract.PART_IDS` 会断言顺序。挂接合计正好 25：

| 部位 | 测点数 | 具体 |
|---|---|---|
| 电机 `motor` | 7 | 电机非驱动端 水平/垂直/轴向/斜45° + 电机驱动端 水平/垂直/轴向 |
| 底座与基础 `base` | 12 | 电机基础上 A~D + 电机基础下 A~D + 泵基础 E~H |
| 驱动端轴承 `front-bearing` | 3 | 泵驱动端 水平/垂直/轴向 |
| 泵本体 `pump-body` | 3 | 泵非驱动端 水平/垂直/轴向 |
| 联轴器 `coupling` | **0** | ★ 报告的 25 个测点里没有联轴器测振点 |
| 机械密封 `seal` | **0** | ★ 振动检测不覆盖机械密封 |

**★ 那两个 0 不是数据缺失，是这一屏最该讲的一句话。** 报告判出「存在不对中」，靠的是
电机-泵驱动端相位差 90° + 100.3Hz 二倍频**推断**，而不是在联轴器上测到了什么。
恰恰因为没有直接测点，它才最需要人去现场看 —— 所以联轴器的状态给 `danger`
（无测振点 + 被结论指名），点进去右栏显示的是空态并写明理由。

机械密封是另一种情况：无测振点、也没有结论指名。它的状态本该靠温度和泄漏检测，
而这台机组在台账里的机封温度阈值**未填报**（与大屏左栏「阈值缺项 40/40」同源）。
所以它的状态点做成**空心灰**而不是绿点 —— 绿点在说「测过了，正常」，实情是「没测」。
`Pump3DContract.STATUSES` 只有 ok/warn/danger 三档、加不了第四种状态，所以这一档
靠 CSS 的 `.no-signal` 区分，验收里有断言盯着它的背景色是透明的。

## 五、部位状态怎么派生（三条规则，顺序即优先级）

1. **有测点** → 严格按 ISO 10186-3 的「部位内最大值」定级，A→ok / B→warn / C,D→danger。
   B 是「良」不是「优」，报告给这台 B 级机组开了三条整改建议，所以 B 不算 ok。
2. **无测点、但被报告结论指名** → danger（联轴器）。
3. **无测点、也没有结论指名** → ok，但 `hasData` 为 false，屏上必须写明「无测振点」。

派生结果：泵本体 A→ok / 电机·底座·驱动端轴承 B→warn / 联轴器 danger / 机封 无数据。
1 danger + 3 warn + 2 ok，视觉层次清楚，而且每个颜色都有一句写得出来的理由。

## 七、两处排版上的实测结论

1. **25 行必须排两列**。单列要 1437px，而右栏那一格只有约 600px，会变成滚动条 ——
   路演大屏不该要人去滚。两列 13+12 一屏放完。选中某个部位之后只剩 3~12 行，
   改回单列（名字不被省略号截断），按行数 ≥13 切。
2. **两列必须列优先填充**（`grid-auto-flow: column` + 显式 `grid-template-rows: repeat(13, auto)`）。
   默认的行优先会排成 左1右2 / 左3右4，顺着左列往下读是 1,3,5,7…，读者会以为漏了一半。
   列优先才是左列 1→13、右列 14→25，与左栏第二张图 x 轴的 1→25 顺序一致。

## 八、3D 层：一字未改

`pump3d/{contract,model,engine}.js`、`vendor/`、`core/` 四个通用文件、`ui/cards.js`
全部相对引用旧目录 `../pump-station-situation/` 的原文件，**不复制副本**。
样式里 `04-charts.css` / `05-pump3d.css` 同样原样复用，它们按旧目录的变量名读色
（`--cyan` / `--blue` / `--green` / `--amber` / `--red` / `--pump-stage-bg`），
所以本目录 `01-tokens.css` 把那几个名字逐条补成三色语义变量的别名 —— 颜色只有一份真源。

⚠️ 两个必须照做的 DOM 契约（改错了会**静默失效**，不报错）：
- 热点结构必须是 `.part-pin > .pin-core + .pin-label`。`.pin-core` 是那个圆点
  （三色 + active 放大 + danger 呼吸），换类名后圆点和状态色整块失效。
- `data-part` 归 3D 热点独占，且必须恰好 6 个、全在 `.pump3d-labels` 内。部位带的卡片
  用的是 `data-part-id`（属性名不同，不会被 `[data-part]` 选中）。复用它会让 engine 的
  `buildLabelMap` 把非 3D 元素收进 `labelEls`，3D 标签会同时消失。

**没有调 `Pump3DContract.assertData()`**：它内部读 `window.DemoData.parts()`，那是旧目录
`scripts/data/catalog.js` 的数据层，本 POC 刻意不加载（它带着 6 步流程、知识库、Agent
语料一整套诊断台的数据）。它真正检查的两件事已经搬进 `measure.js` 的 `assertMapping()`，
而且更严：原版只查部位 id 集合，那边连顺序一起查。3D 侧的检查一条没少 —— `mount()` 里
仍有 `assertDom()`，`render()` 末尾仍有 `assertPinNamespace()`。
