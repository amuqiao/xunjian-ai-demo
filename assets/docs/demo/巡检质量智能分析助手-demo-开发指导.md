# 巡检质量智能分析助手 demo 开发指导

本文是参赛 demo 的开发执行指导，用于把现有轻量 FastAPI 骨架落成一套可演示、可讲清、可分阶段实现的竞赛作品。

本文不替代对外口径和技术定版方案。业务定位、演示范围和验收口径见 [巡检质量智能分析助手-demo-AI赋能演示定稿方案.md](巡检质量智能分析助手-demo-AI赋能演示定稿方案.md)，固定技术栈、架构分层和 API 边界见 [巡检质量智能分析助手-demo-技术实施定版方案.md](巡检质量智能分析助手-demo-技术实施定版方案.md)。

## 1. 我对诉求的理解

你要做的不是一个普通 CRUD 系统，也不是完整生产级巡检平台，而是一套用于人工智能创新大赛的参赛 demo。

核心诉求可以压缩成一句话：

```text
在轻量骨架上做出一套视觉冲击强、业务逻辑顺、评委能快速理解价值的巡检质量智能分析 demo，
用固定样例数据跑通“发现疑点 -> 命中依据 -> 生成复检 -> 人工确认 -> 自动报告 -> 案例沉淀”的闭环。
```

这份指导文档要解决的问题是：

| 问题 | 本文给出的答案 |
| --- | --- |
| 这个 demo 该怎么讲才适合参赛拿奖 | 用 5-8 分钟固定演示剧本，突出“可执行、可决策、可复用、可进化”。 |
| 需要哪些页面 | 控制在 4 个主页面，外加一个可选 Agent 抽屉，不做大而全平台。 |
| 需要造哪些假数据 | 只造 1 套主剧情数据包和 1 套正常对照数据包，所有结论可追溯。 |
| 需要你提供什么真实资料 | 时序数据、现场图片/视频帧、真实复检案例、报告模板、阈值口径。 |
| 什么格式最适合开发 | 原始时序可用 CSV / Excel 提供；进入 demo 场景包后按技术实施方案统一整理为 JSON seed。 |
| 怎么分阶段实现 | 先冻结场景，再做后端 seed/规则/报告，再做前端 4 页和演示效果，最后验证。 |

## 2. Demo 心智模型

参赛 demo 的重点不是功能数量，而是让评委看到 AI 把分散数据串成了可执行闭环。

```text
附件资料 / 样例数据
  -> 场景包 scenario-a
  -> 后端规则计算和证据链
  -> 前端 4 页演示
  -> 复检确认
  -> 报告快照
  -> 案例归档
```

每个页面都必须回答一个问题：

| 页面 | 回答的问题 | 评委看到的价值 |
| --- | --- | --- |
| 任务简报 | 今天 AI 发现了什么风险 | 从人工翻记录变成系统主动提示。 |
| 巡检分析 | 这个风险为什么成立 | 表单、曲线、图片和规则证据被自动关联。 |
| 复检工作台 | 下一步该怎么复核 | Agent 把依据、步骤和补拍建议整理成动作清单。 |
| 报告归档 | 结果如何沉淀复用 | 自动生成交接班关注项和案例摘要。 |

## 3. 参赛演示主线

本节复述 [巡检质量智能分析助手-demo-AI赋能演示定稿方案.md](巡检质量智能分析助手-demo-AI赋能演示定稿方案.md) 中已经确认的默认故事。若业务方后续调整站点、区域或检查项，以对外定稿方案为唯一口径，本文只同步开发执行细节。

默认主线建议沿用：

```text
已确认默认场景 scenario-a
  -> 实际开始时间晚于计划时间
  -> 过滤器差压 72 小时内缓慢抬升并接近预警线
  -> 巡检表单仍填写“正常”
  -> 电动执行机构指示灯图片作为视觉加演
  -> 知识库命中差压阈值、巡检标准和复检步骤
  -> Agent 生成复检清单和补拍建议
  -> 人工确认复检结论
  -> 自动生成巡检摘要、交接班关注项和案例归档
```

这条主线的优势：

| 维度 | 原因 |
| --- | --- |
| 业务上容易讲 | 计量区、差压、表单正常但数据异常，冲突清楚。 |
| 视觉上容易做 | 曲线、阈值线、异常窗口、图片框选都有直观画面。 |
| 技术上可落地 | 轻量规则和固定 seed 就能完成，不依赖模型训练。 |
| 参赛上有亮点 | 同时体现多源融合、复检决策、报告沉淀和可复制场景包。 |

## 4. 5-8 分钟演示剧本

| 时间 | 演示动作 | 页面 | 讲解重点 |
| --- | --- | --- | --- |
| 0:00-0:40 | 打开首屏，展示站场、任务、风险评分和 3 个疑点 | 任务简报 | 这不是重做巡检系统，而是让系统主动发现疑点。 |
| 0:40-1:30 | 点击本轮巡检任务，展示计划时间、实际时间、人员和到位疑点 | 任务简报 | 人工核查巡检资料的工作被自动质检压缩。 |
| 1:30-3:00 | 进入巡检分析页，聚焦过滤器差压曲线和表单“正常”冲突 | 巡检分析 | AI 不是只看单点告警，而是发现趋势偏移和填报矛盾。 |
| 3:00-3:40 | 切到现场图片，展示识别框、状态标签和置信度 | 巡检分析 | 视觉识别只作为证据增强，不承诺替代全部人工巡检。 |
| 3:40-4:50 | 打开复检工作台，展示标准依据、复检步骤、补拍建议 | 复检工作台 | 系统把疑点转成可执行复检动作。 |
| 4:50-5:40 | 人工确认复检结论，状态从待确认切换为已确认 | 复检工作台 | 安全生产边界保留人工确认，AI 做辅助判断。 |
| 5:40-6:40 | 生成报告快照，展示巡检摘要、交接班关注项和案例标签 | 报告归档 | 报告和经验沉淀不再靠人工汇总。 |
| 6:40-7:30 | 可选打开 Agent 抽屉，点击固定问题 | 全局抽屉 | 呼应数智员工，但不做开放式问答。 |
| 7:30-8:00 | 回到首屏收束，展示闭环完成 | 任务简报 | 发现更早、核查更省、经验可沉淀。 |

## 5. 页面与效果方案

### 5.1 页面 1：任务简报

路由建议：`/`

页面目标：让评委在第一眼看到这是一个“工业 AI 智控驾驶舱”，不是普通列表页。

首屏结构：

| 区域 | 内容 | 效果 |
| --- | --- | --- |
| 顶部任务条 | 站场、日期、当前任务、演示步骤 | 深色壳层，状态标签高亮。 |
| 风险总览 | 风险评分、疑点数量、待复检数量、报告状态 | 数字翻牌一次，不持续闪烁。 |
| 主流程 | 数据进入、AI 分析、复检、报告、归档 | 横向步骤条逐段点亮。 |
| 疑点胶囊 | 迟到、差压趋势异常、表单正常但数据异常 | 点击后跳转并定位证据。 |

实现边界：

- 不做真实人员考核和扣分。
- 不做复杂地图或 3D 站场。
- 首屏文案要短，投屏下无需读长段文字。

### 5.2 页面 2：巡检分析

路由建议：`/inspection/:taskId`

页面目标：把表单、时序、图片和 AI 提醒联动起来，制造主冲突。

布局建议：

```text
左侧：精选巡检项表格
右上：过滤器差压趋势图
右中：现场图片 / 视频帧证据
右下：AI 提醒和证据链入口
```

核心效果：

| 效果 | 实现方式 | 价值 |
| --- | --- | --- |
| 阈值线和异常窗口 | ECharts `markLine`、`markArea` | 一眼看出趋势接近预警线。 |
| 表单行联动图表 | 点击表格行，高亮对应时间窗和证据图片 | 证明不是孤立图表。 |
| 图片识别框 | 在图片上叠加 bbox 和标签 | 视觉效果直观，开发成本低。 |
| 冲突提示 | “时序异常，但表单填写正常”红色提示卡 | 形成演示记忆点。 |

### 5.3 页面 3：复检工作台

路由建议：`/recheck/:taskId`

页面目标：让评委看到系统不是只报警，而是能给出依据和下一步动作。

建议做成“三联证据台”：

| 模块 | 内容 |
| --- | --- |
| 异常说明 | 疑点等级、触发规则、关联设备、时间窗口。 |
| 知识依据 | 巡检标准、阈值口径、复检步骤、历史案例。 |
| 复检清单 | 复核点位、补拍建议、人工确认项、确认备注。 |

核心效果：

- 点击疑点时右侧 Drawer 打开完整证据链。
- 命中的标准条款做高亮。
- 人工确认后 checklist 从“待确认”切到“已确认”，并触发报告可生成状态。

### 5.4 页面 4：报告归档

路由建议：`/reports/:taskId`

页面目标：像高层摘要页，不像 Word 预览页。

内容结构：

| 区域 | 内容 |
| --- | --- |
| 任务结论 | 本次任务是否完成、关键疑点、复检状态。 |
| 巡检摘要 | 到位情况、表单疑点、AI 异常提示。 |
| 交接班关注项 | 未闭环风险、后续关注设备、建议动作。 |
| 案例归档 | 案例标题、标签、证据来源、复用说明。 |
| 版本信息 | 数据版本、规则版本、模板版本、生成时间。 |

核心效果：

- 报告分段渐显。
- 顶部显示“已生成报告快照”和版本章。
- 用一个收束动画展示“原始疑点 -> 已复检 -> 已归档”。

### 5.5 可选：Agent 抽屉

不要新增聊天页面。建议做全局浮动 Agent 抽屉，只允许固定问题：

| 固定问题 | 输出 |
| --- | --- |
| 为什么这个差压趋势需要复检 | 标准依据、阈值、趋势窗口。 |
| 本次巡检有哪些质量疑点 | 到位、表单、时序、视觉联动摘要。 |
| 复检人员需要补拍什么 | 点位、角度、照片要求。 |
| 交接班需要关注什么 | 后续关注设备、建议动作、未闭环项。 |

不要承诺“随便问都能答”。首版 Agent 是固定场景内的报告和复检助手。

## 6. 需要准备的数据

### 6.1 最小场景包

首版只需要一套主剧情数据包：

| 数据对象 | 数量 | 来源 | 说明 |
| --- | --- | --- | --- |
| 巡检任务 | 1 条主任务，1 条正常对照任务 | 附件2 + 人工整理 | 主任务用于演示异常闭环，对照任务用于展示不是全量报错。 |
| 巡检项 | 8-12 条 | 附件2巡检记录 | 只选代表项，不搬完整表单。 |
| 时序点 | 48-72 小时，15 分钟粒度 | 你提供或演示构造 | 过滤器差压默认主线。 |
| 视觉结果 | 1-3 张图片和识别结果 | 你提供现场图或视频帧 | 电动执行机构、压力表、阀位任选 1 个主项。 |
| 规则 | 4-6 条 | 附件标准 + 演示口径 | 迟到、漏填、趋势异常、表单矛盾、视觉联动。 |
| 知识条目 | 5-8 条 | 附件1/附件2 | 标准、阈值、复检步骤、案例、报告模板。 |
| 演示脚本 | 1 份 | 开发维护 | 控制默认任务、默认步骤、默认高亮。 |
| 报告模板 | 1 份 | 你确认或附件整理 | 巡检摘要、复检清单、交接班关注项。 |

时序数据建议：

- 时间跨度：48-72 小时。
- 粒度：15 分钟优先；无法提供时，可用 30 分钟或 1 小时。

- 必须提供单位、阈值口径和采样时间，不要只给一列数字。
- 如果你提供的是 CSV / Excel，开发阶段先转换成上面的 JSON seed，再导入 PostgreSQL。

## 8. 需要你提供的素材

### 8.1 优先级 P0：没有会影响主线可信度

| 素材 | 建议格式 | 数量 | 用途 |
| --- | --- | --- | --- |
| 过滤器差压或压力趋势数据 | CSV / Excel | 48-72 小时，15 分钟粒度优先 | 做时序曲线、阈值线、异常窗口。 |
| 巡检表单样例 | Excel / Word / Markdown / 图片 | 1 份 | 提取 8-12 条精选巡检项。 |
| 巡检标准和阈值口径 | Word / Excel / Markdown | 1 份 | 支撑知识库依据和规则解释。 |
| 报告或交接班模板 | Word / Markdown | 1 份 | 支撑报告快照结构。 |

### 8.2 优先级 P1：增强演示现场感

| 素材 | 建议格式 | 数量 | 用途 |
| --- | --- | --- | --- |
| 电动执行机构、阀位、压力表或机柜指示灯近景 | JPG / PNG | 3-5 张 | 做视觉识别框和表单联动。 |
| 监控视频关键片段 | MP4 | 1-3 段，每段 10-30 秒 | 只截关键帧，不做实时视频推理。 |
| 真实异常或复检案例 | Word / Markdown / 口述整理 | 1 条 | 做案例归档，增强说服力。 |
| 站场或设备环境图 | JPG / PNG | 1-3 张 | 做首屏背景或任务简报配图。 |

### 8.3 优先级 P2：后续加分项

| 素材 | 用途 |
| --- | --- |
| 多站点设备点位表 | 支撑“可复用”扩展说明。 |
| 人员到位轨迹或签到点 | 支撑路线覆盖加演。 |
| 历史巡检统计 | 支撑管理侧趋势看板。 |
| 真实 WeAct / IMS 字段样例 | 支撑半真实集成阶段。 |

## 9. 假数据设计原则

假数据不是随便编。它要服务演示冲突，并且能被规则和证据解释。

| 原则 | 做法 |
| --- | --- |
| 有主冲突 | 设计“时序异常但表单正常”的矛盾。 |
| 有辅助冲突 | 设计“实际开始晚于计划时间”的到位疑点。 |
| 有视觉记忆点 | 设计 1 张图片识别结果和表单结果不一致。 |
| 有闭环动作 | 每个疑点都能生成复检建议和人工确认项。 |
| 有证据来源 | 每个结论都能回到规则、表单、时序、图片或知识条目。 |
| 有正常对照 | 额外准备 1 条正常任务，证明系统不是全量标红。 |

禁止做法：

- 不要为了“更稳”在数据缺失时静默生成默认结论。
- 不要让前端直接拼出业务判断。
- 不要让报告引用不存在的证据。
- 不要把演示数据包装成真实生产结论。

## 10. 工程落地路径

当前仓库是 `fastapi-lite` 后端骨架，已经具备 FastAPI、SQLAlchemy async、Alembic、UnitOfWork、repository、OpenAPI、统一 envelope 和验证脚本。当前还没有 React 前端、demo 业务模型、seed 导入和报告模板。

开发顺序建议：

| 顺序 | 目标 | 关键产物 |
| --- | --- | --- |
| 1 | 冻结场景包 | `scenario-a` 数据清单、规则口径、演示脚本、报告模板。 |
| 2 | 新增后端数据模型 | 任务、巡检项、时序点、视觉结果、规则、证据、疑点、复检、报告快照。 |
| 3 | 新增 seed 导入 | JSON seed 导入 PostgreSQL，缺字段直接失败；CSV / Excel 原始资料先转换。 |
| 4 | 新增规则计算 | 到位、表单、时序、视觉联动规则生成 `Finding` 和 `Evidence`。 |
| 5 | 新增复检和报告服务 | 生成复检清单、保存人工确认、生成报告快照。 |
| 6 | 搭建前端 4 页 | React + Vite + TypeScript + Ant Design + ECharts。 |
| 7 | 做演示效果 | 首屏驾驶舱、图表联动、bbox、高亮、报告渐显。 |
| 8 | Docker Compose 演示交付 | frontend、backend、postgres、readonly seeds/assets、runtime reports。 |

首版开发可以按 4 个页面组织集成顺序，但不重新定义 API 合同。外部路由前缀、数据模型和 OpenAPI 以 [巡检质量智能分析助手-demo-技术实施定版方案.md](巡检质量智能分析助手-demo-技术实施定版方案.md) 为准。

| 页面集成顺序 | 主要读取/写入内容 | 验收重点 |
| --- | --- | --- |
| 任务简报 | 默认任务、演示步骤、风险总览 | 首屏能讲清本轮风险。 |
| 巡检分析 | 表单项、时序图、图片、视觉结果、疑点 | 表单、曲线、图片能联动。 |
| 复检工作台 | 复检清单、知识依据、人工确认 | 疑点能转成复检动作。 |
| 报告归档 | 报告生成、报告快照、案例摘要 | 报告能保存并追溯版本。 |

`knowledge`、`rules`、`evidence` 是否暴露为独立路由，由技术实施方案和 OpenAPI 合同决定；本文只约束页面开发顺序和演示验收。

## 11. 分阶段实现目标

### 阶段 0：场景冻结

目标：开发前先把演示主线和数据合同钉住。

完成标准：

- 确认是否沿用对外定稿方案默认场景：计量区例行巡检。
- 确认时序检查项：过滤器差压优先。
- 确认视觉检查项：电动执行机构、阀位或压力表任选 1 个。
- 确认巡检质检点：迟到、漏填、异常未说明、数据异常但填正常中选 1-2 个。
- 确认知识库材料：标准、阈值、复检步骤、案例、报告模板。
- 确认演示脚本：4 页路径、点击顺序、默认高亮疑点。

### 阶段 1：后端闭环

目标：不用前端也能通过 API 跑通 `任务 -> 疑点 -> 依据 -> 复检 -> 报告`。

完成标准：

- seed 可导入 PostgreSQL。
- 后端能生成疑点和证据链。
- 复检清单可生成和人工确认。
- 报告快照可生成并保存版本信息。
- OpenAPI 能展示关键 API 合同。

### 阶段 2：前端主流程

目标：4 个页面可以点击演示，先保证主线顺畅。

完成标准：

- 任务简报能展示默认任务和风险总览。
- 巡检分析能展示表单、曲线、图片和 AI 提醒。
- 复检工作台能展示依据、清单和人工确认。
- 报告归档能展示报告快照和案例摘要。
- 页面刷新后仍能从后端读取确认和报告状态。

### 阶段 3：参赛视觉增强

目标：把演示从“能跑”提升到“像参赛作品”。

完成标准：

- 深色工业智控壳层完成。
- 首屏风险总览、步骤点亮、数据源连线完成。
- 图表阈值线、异常窗口、表单联动完成。
- 图片 bbox 和热点高亮完成。
- 报告分段渐显和闭环收束完成。
- 全局 Agent 抽屉只保留固定问题。

### 阶段 4：演示交付

目标：固定机器上能稳定演示，团队能按脚本讲完。

完成标准：

- Docker Compose 或本地脚本能一键启动目标演示环境。
- `scenario-a` 可重置。
- 演示账号、浏览器窗口、投屏分辨率和素材路径固定。
- 5-8 分钟讲解稿和点击脚本完成。
- 演示前检查清单完成。

### 阶段 5：半真实集成

目标：比赛后或下一阶段只接一个真实入口，不推翻 demo 架构。

可选方向：

- 接 1 个真实时序数据导入。
- 接 1 个真实视觉识别结果。
- 接 1 个真实 IMS 巡检样例。
- 接 1 个真实报告模板。

每次只接一个方向，并保持 `Finding -> Evidence -> Recheck -> ReportSnapshot` 证据链不变。

## 12. 验收与验证

开发阶段最小验证：

| 阶段 | 验证 |
| --- | --- |
| 文档和场景冻结 | 检查链接、数据清单、脚本是否完整。 |
| 后端模型和 API | 跑单元测试、OpenAPI 合同检查、迁移检查。 |
| seed 导入 | 用缺字段样例确认导入会失败，用完整样例确认可导入。 |
| 前端页面 | 本地运行，按 4 页脚本点击一遍。 |
| 图表和图片 | 检查阈值线、异常窗口、bbox 是否和数据一致。 |
| 报告快照 | 刷新页面后报告仍展示同一版本结论。 |
| 演示交付 | 在目标演示机器完整跑一遍 5-8 分钟脚本。 |

最终声称完成前至少运行：

```bash
./scripts/verify.sh check
```

涉及 PostgreSQL 迁移和集成时再运行：

```bash
./scripts/verify.sh postgres
./scripts/verify.sh migration-roundtrip
```

如果后续新增前端工程，需要补充前端 lint、typecheck、build 和页面截图验证。

## 13. 明确不做

两周参赛 demo 不做：

| 不做项 | 原因 |
| --- | --- |
| 3D 站场地图 / 数字孪生 | 成本高，容易偏离证据闭环。 |
| 实时视频推理 | 接口、算力、稳定性不可控。 |
| 开放式大模型聊天 | 验收不可控，容易答偏。 |
| 真实 PI / IMS / WeAct 联调 | 会变成系统集成项目。 |
| 训练 YOLO / OCR / 深度时序模型 | 需要样本、标注、评测和算力。 |
| 正式派单、审批、销项 | 涉及生产责任和权限审计。 |
| 正式人员考核扣分 | 演示态只做疑点提示和人工确认。 |
| 完整报表中心 | 首版只做一份报告快照。 |
| PDF / Excel 精致导出 | 页面报告优先，导出是后续增强。 |
