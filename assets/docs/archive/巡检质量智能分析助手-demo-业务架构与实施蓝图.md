## 1. 文档目标

这份文档要帮助你在和业务方沟通时完成 5 件事：

1. 把业务方的愿景材料翻译成清晰业务逻辑。
2. 让业务方理解 demo 不是几个页面，而是一条巡检质量分析闭环。
3. 明确 demo 要证明什么、展示什么、做到什么深度。
4. 把功能拆成业务方能逐项拍板的确认项。
5. 为后续排期、报价、开发和验收建立依据。

会议中不要一上来讨论 React、FastAPI、YOLO、WeAgent 或 PI 接口。建议先讲清：

> 我们先不讨论系统怎么写代码，而是先确认这个 demo 到底要证明什么业务价值。只有业务闭环确认清楚，技术实现、工期和报价才有依据。

## 2. 业务方原始想法摘要

根据业务材料，业务方想表达的不是单一功能，而是一套巡检质量智能分析能力：

| 原始表达 | 可落地翻译 |
| --- | --- |
| 机器视觉智能感知、IMS 智能巡检、WeACT 消息推送一体化运维底座 | 现有系统已有设备感知、人员巡检、消息触达等数据来源，但缺少统一分析闭环。 |
| 机器视觉仅输出瞬时设备告警 | 设备侧需要从“某次告警”升级到“长期趋势、健康等级、维保建议”。 |
| 人工周期性巡检靠管理人员人工核查 | 人员侧需要自动判断漏巡、迟巡、照片异常、填报不规范、疑似虚假取证。 |
| 设备自动巡检、人员现场巡检数据孤岛 | 需要把设备异常和人员履职质量关联起来，识别复合安全风险。 |
| 巡检异常、履职考核、故障台账依靠人工汇总 | 需要自动生成风险清单、人员履职台账、设备趋势报表、闭环记录。 |
| 聊天窗口 + 极简页面 | 交互要轻量，让管理人员和一线人员快速查询风险、报表、建议。 |
| WeAgent、Coze、PIPENET、知识库、Skill、评测集 | 这是未来平台化和复用方向，不应默认全部进入第一版 demo。 |

业务材料里混合了三层内容，会议中必须拆开：

| 层级 | 含义 | 对 demo 的处理 |
| --- | --- | --- |
| 业务痛点 | 人工核查累、设备趋势看不到、复合风险识别不了、报表靠人工 | 第一版必须围绕这些痛点证明价值。 |
| 立项亮点 | 双引擎、多源融合、复合风险、自动报表、可复用 AI 资产 | demo 要重点展示其中最有说服力的闭环。 |
| 远期愿景 | 全场站覆盖、真实四源打通、知识图谱、模型迭代、集团复用 | 第一版只做可说明、可预留，不直接承诺交付。 |

## 3. 核心心智模型

这个项目的本质不是“再做一个巡检系统”，也不是“做一个 AI 聊天机器人”，而是：

> 巡检质量智能分析助手：把设备有没有变坏、人员有没有认真巡、风险有没有闭环，放到同一个分析闭环里自动判断。

现有巡检体系通常已经有这些东西：

```text
设备数据
  PI 时序参数 / 视觉识别结果 / 设备台账

人工巡检数据
  IMS 巡检计划 / 打卡轨迹 / 现场照片 / 隐患填报

消息与管理数据
  WeAct 通知 / 风险记录 / 台账 / 报表
```

但核心问题是：

```text
数据被记录了
  但没有被统一分析

异常被看到了
  但没有形成长期趋势判断

人员巡检留下痕迹了
  但履职质量仍靠人工核查

设备异常和人员漏检同时发生了
  但没有被系统识别为更高风险

报表和台账能人工做出来
  但不能自动沉淀为管理依据
```

所以 demo 的心智模型应当是：

```text
设备侧：设备是否正在变坏？
人员侧：人员是否真的巡到了、巡好了？
关联侧：设备异常和人员漏检是否叠加成复合风险？
输出侧：风险、解释、建议、报表、台账是否能自动生成？
```

这决定了第一版 demo 的重点不是页面数量，而是闭环完整度。

## 5. 角色与使用场景

demo 不需要做完整权限系统，但需要让业务方看到不同角色为什么需要这个助手。

| 角色 | 关心什么 | demo 中应该看到什么 |
| --- | --- | --- |
| 一线运维人员 | 今天哪里风险高、需要补充什么、怎么整改 | 风险提醒、设备健康状态、处置建议、整改状态。 |
| 值班工程师 / 站场管理人员 | 哪些设备异常、谁没巡好、是否影响安全生产 | 设备趋势、人员履职评分、复合风险原因、待处理清单。 |
| 生产部 / 管理层 | 整体巡检质量、人员趋势、设备隐患趋势、管理成效 | 首页概览、排名、趋势报表、闭环率、减负价值。 |
| 督查 / 考核人员 | 扣分依据是否客观、是否可追溯 | 证据链、照片、轨迹、命中规则、评分明细。 |
| 技术 / 推广方 | 能否复用到其他场站 | 点位配置、规则配置、数据适配器、后续扩展路径。 |

会议中建议这样说：

> 这个 demo 不是只给一线人员用，也不是只给领导看大屏。它要同时说明一线怎么减负、管理怎么提效、督查怎么有依据、后续怎么复制。

## 6. demo 要证明什么

第一版 demo 最少要证明 4 件事：

1. 设备侧能从瞬时告警升级为长期趋势研判。
2. 人员侧能从人工核查升级为自动履职评价。
3. 设备异常和人员漏检能被系统关联为复合风险。
4. 系统能输出可追溯的风险、建议、台账和报表。

建议演示主线：

```text
某站场某设备连续多日轻微异常
  -> 视觉读数和远传参数存在偏差
  -> 对应点位最近几次人工巡检存在漏巡 / 照片重复 / 填报不规范
  -> 系统自动识别为复合风险
  -> 生成风险解释、处置建议、人员扣分和报表台账
  -> 管理人员通过页面或聊天查询原因和证据
```

这个故事比“做很多页面”更重要，因为它能让业务方看到差异化：

| 传统方式 | demo 要展示的变化 |
| --- | --- |
| 只看到单次设备告警 | 看到趋势、健康等级、维保建议。 |
| 管理人员逐条翻巡检资料 | 系统自动指出漏巡、照片异常、填报异常。 |
| 设备数据和人员数据分开看 | 系统自动识别“设备异常 + 人员漏检”复合风险。 |
| 报表靠人工汇总 | 系统自动生成设备趋势、人员履职、风险闭环台账。 |
| 查询靠熟悉系统菜单 | 聊天窗口或极简页面直接查风险和原因。 |

| 业务层 | 推荐技术实现 | 说明 |
| --- | --- | --- |
| 用户交互层 | `React / Vite` Web 页面，必要时复用现有工作台骨架 | 重点是业务可信、演示稳定，不追求完整产品级 UI。 |

> 页面承载主展示，聊天只做快捷查询入口。若时间或预算收紧，优先保留页面闭环、报表台账和复合风险解释，聊天降为固定意图入口。

## 9. 功能点确认表

下面这张表用于和业务方逐项拍板。不要直接问“要不要做设备研判”，而要问清楚数据、规则、展示效果和实现深度。

| 业务想法 | demo 需要确认的问题 | 推荐第一版 | 取舍理由 |
| --- | --- | --- | --- |
| 设备时序研判 | 看哪类设备？看哪些参数？历史周期多长？异常规则是什么？ | 选 1 类设备，做真实轻量趋势分析 | 它是“从瞬时告警到趋势研判”的核心证明点，必须真实算。 |
| 机器视觉识别 | demo 是否自己识别图片？还是展示已有识别结果？ | 用预置识别结果，不训练 YOLO | 业务资料已有视觉能力，demo 重点是识别结果如何进入巡检质量闭环。 |
| 视觉与远传交叉校验 | 哪个视觉读数与哪个 PI 参数对比？容差多少？ | 做 1 个典型对比样例 | 能增强设备侧可信度，但不需要全量点位。 |
| 人员履职评价 | 漏巡、迟巡、照片重复、填报不规范怎么定义？ | 做 2-3 条明确规则 | 人员质控是区别于普通视觉巡检系统的核心。 |
| 虚假取证识别 | 用 GPS、时间、照片相似度、画面内容，还是人工标注样例？ | 第一版用规则和预置证据展示 | 若做真实图像相似度或定位校验，需要更多样本和算法验证。 |
| 复合风险升级 | 哪种组合算高风险？谁拍板？ | 做 1 个典型故事 | 这是最强差异化：设备异常和人员漏检被关联起来。 |
| 聊天窗口 | 是固定问答、限定意图，还是开放 Agent？ | 限定 3-5 个业务意图 | 开放 Agent 验收不可控；限定意图足够支撑演示。 |
| 极简页面 | 是否需要首页、设备、人员、风险、报表全部展示？ | 做 4-6 个核心页面 | 页面服务演示闭环，不做大而全后台。 |
| 报表台账 | 要哪些报表？页面展示还是导出？ | 固定 2-3 个模板 | 报表支撑管理汇报，但临时新增模板会扩大范围。 |
| WeAct 闭环 | 只是模拟通知，还是接真实消息？ | 第一版模拟通知和状态流转 | 真实接口会引入权限、网络、联调和验收风险。 |
| PI / IMS 接入 | 真接系统还是用样例数据？ | 第一版模拟，预留适配器 | 真实接入需要接口、字段、测试环境和数据脱敏。 |
| 多模态能力 | 图片是否入模？模型是否参与判定？ | 可选做解释，不做裁决 | 安全生产场景不建议让模型直接决定风险等级或考核结果。 |
| 知识图谱 / 六大知识库 | 是否必须展示图谱界面？ | 首版用最小规则表替代 | 完整知识图谱属于正式项目基础能力。 |

## 10. 展现形式确认表

demo 的展示形态会直接影响工期和报价，必须单独确认。

| 形态 | 说明 | 适用场景 | 风险 |
| --- | --- | --- | --- |
| 可点击原型 | 页面像系统，逻辑多为静态或半静态 | 时间很紧，只为讲概念 | 容易被认为只是原型，不证明分析能力。 |
| 可交互模拟 PoC | 有模拟数据、真实规则计算、报表和聊天 | 最推荐，适合立项演示 | 需要业务方接受模拟数据边界。 |
| 半真实集成 demo | 在 PoC 基础上接 1 个真实系统或真实模型 | 业务方已有接口和测试环境 | 联调和权限会影响周期。 |
| 试点 MVP | 接真实数据、真实流程、真实部署 | 已经接近正式项目 | 不应按 demo 报价和验收。 |

建议会议中直接推动业务方选择：

> 如果目标是立项演示，我建议做可交互模拟 PoC。它不是静态页面，分析逻辑是真的；但数据、通知、接口先模拟。这样既能打动业务，也能控制工期。

## 11. 实现深度分档

这张表用于谈判和报价。业务方如果要求更高档位，就必须接受更高工期、更多资源和更强验收约束。

| 档位 | 定位 | 做什么 | 不做什么 | 适用情况 | 推荐度 |
| --- | --- | --- | --- | --- | --- |
| A 档：可点击原型 | 把方案讲明白 | 页面流程、静态数据、演示文案、少量交互 | 不做真实计算、不接模型、不接接口 | 预算低、时间极短、只为汇报概念 | 可选 |
| B 档：可交互模拟 PoC | 把业务闭环跑通 | 模拟四源数据、真实规则计算、轻量时序、风险升级、报表、限定聊天 | 不接真实四源、不训练模型、不做真实闭环 | 立项演示最合适 | 推荐 |
| C 档：半真实集成 demo | 把一个关键接缝接真 | B 档基础上接 1 个真实接口或 1 个真实模型 | 不承诺全量生产流程 | 业务方能提供接口、账号、测试环境 | 条件具备再做 |
| D 档：试点 MVP | 进入真实业务验证 | 真实数据、真实部署、真实闭环、联调验收、权限审计 | 不再按 demo 管理 | 立项后试点阶段 | 另立项目 |

档位判断话术：

> 如果接受模拟数据和限定意图，走 B 档；如果必须接 1 个真实接口或模型，走 C 档；如果必须真实部署、真实闭环、真实算法验证，那就是 D 档，已经不是普通 demo。

## 12. 推荐第一版方案

综合业务价值、演示说服力、开发可控性，推荐第一版采用：

> B 档：可交互模拟 PoC。

推荐范围：

| 维度 | 第一版范围 |
| --- | --- |
| 场景 | 1 个站场或 1 个业务区域。 |
| 设备 | 1 类典型设备，例如仪表、阀门、红外测温、机柜状态中的一种。 |
| 设备数据 | 1 组正常样例、1 组异常趋势样例、1 组视觉与远传偏差样例。 |
| 人员规则 | 2-3 条巡检质控规则，例如漏巡、照片重复、填报不规范。 |
| 复合风险 | 1 条完整故事：设备持续异常 + 人员漏检 / 低质量巡检。 |
| 页面 | 首页概览、设备详情、人员履职、复合风险、报表台账、聊天入口。 |
| 报表 | 2-3 个固定模板：设备趋势报表、人员履职台账、综合风险清单。 |
| 聊天 | 3-5 个限定业务意图。 |
| 闭环 | demo 内模拟通知、确认、整改状态和台账留痕。 |

推荐实现方式：

| 能力 | 第一版实现 |
| --- | --- |
| PI 时序数据 | 模拟数据或离线文件。 |
| IMS 巡检数据 | 模拟打卡、路线、照片、填报记录。 |
| 机器视觉结果 | 预置识别结果，不训练 YOLO。 |
| WeAct 通知 | 模拟消息和状态流转。 |
| 设备趋势分析 | 真实轻量计算，例如阈值、斜率、滚动均值、异常分数。 |
| 人员履职评价 | 真实规则计算，输出扣分项和证据。 |
| 复合风险升级 | 真实规则关联设备异常和人员质控问题。 |
| 报表台账 | 根据真实计算结果生成固定模板。 |
| 大模型 | 可选，只做解释、摘要、建议润色，不做裁决。 |

推荐展示效果：

1. 首页能一眼看到设备风险、人员履职、复合风险、待处置事项。
2. 设备详情能看到曲线、异常段、健康等级、判断依据。
3. 人员履职能看到扣分项、照片 / 打卡 / 填报证据。
4. 复合风险能解释为什么风险升级。
5. 报表台账能支撑管理汇报。
6. 聊天入口能查询固定业务问题。

## 13. 真实性边界

为避免业务方把模拟数据、真实逻辑、AI 模型混在一起，建议统一使用 3 个标签：

| 标签 | 含义 |
| --- | --- |
| `M` | Mock，模拟数据或演示状态。 |
| `R` | Real Logic，真实计算逻辑。 |
| `AI` | AI Enhance，模型增强能力。 |

第一版建议边界：

| 模块 | 数据 / 状态 | 逻辑 | 模型 | 说明 |
| --- | --- | --- | --- | --- |
| PI 时序 | `M` | `R` | 可选 | 数据可模拟，但趋势分析应真实计算。 |
| 机器视觉上游识别结果 | `M` | 不承诺 | 可选 | 第一版使用预置识别结果，不代表现场实时视觉识别或 YOLO 模型训练已经完成。 |
| 基于视觉结果的风险判断 | `M` 数据 | `R` | 可选 | 系统真实把视觉读数、状态或图片标签纳入设备研判和复合风险判断。 |
| IMS 巡检 | `M` | `R` | 不必 | 模拟巡检记录，真实计算履职评分。 |
| WeAct 消息 | `M` | 可选 `R` | 不必 | 首版模拟通知和状态，不做真实推送。 |
| 设备健康等级 | `M` 数据 | `R` | 可选 | 规则或轻量算法真实输出等级。 |
| 人员扣分 | `M` 数据 | `R` | 不必 | 根据冻结规则真实扣分。 |
| 复合风险升级 | `M` 数据 | `R` | 不必 | 必须真实规则关联，这是核心价值。 |
| 报表台账 | `M` 数据 | `R` | 可选 | 从计算结果生成，不做纯静态截图。 |
| 聊天查询 | `M` 数据 | `R` 查询 | 可选 `AI` | 限定意图先查结构化结果，再生成回答。 |

必须讲清楚的 4 个不要混淆：

1. 预置视觉结果不等于做了视觉模型训练。
2. 模板或 LLM 回答不等于开放式智能体。
3. 最小规则表不等于完整知识图谱。
4. 模拟通知和状态流转不等于真实生产闭环。

会议话术：

> 数据可以是模拟的，但分析逻辑、风险升级、证据追溯和报表生成必须是真的算出来。这样 demo 才不是 HTML 动画，也不会因为真实接口联调把项目拖成正式集成项目。

责任边界必须同时讲清：

> 第一版 demo 输出仅用于演示、规则确认和立项沟通，不直接作为正式绩效考核、责任认定、生产处置、派单审批或审计依据。人员扣分 / 评分只按冻结样例和冻结规则演示；复合风险只作为辅助预警，正式业务必须保留人工复核；通知和状态流转只代表 demo 内闭环，不等于真实生产闭环。

## 14. 取舍依据

不要直接说“这个不做、那个模拟”。取舍应按下面逻辑讲：

```text
业务想法是什么
  -> demo 要证明什么
  -> 这个能力对证明目标是否关键
  -> 如果关键，做到什么深度
  -> 如果不关键，是否模拟或后置
  -> 如果业务方坚持真实实现，工期和报价如何变化
```

建议取舍表：

| 能力 | 是否关键 | 推荐 | 理由 |
| --- | --- | --- | --- |
| 复合风险升级 | 关键 | 必须真实做规则 | 这是方案差异化核心，不能只做页面假效果。 |
| 设备趋势分析 | 关键 | 做轻量真实计算 | 证明不是瞬时告警，也不是纯页面演示。 |
| 人员履职评价 | 关键 | 做 2-3 条真实规则 | 直接回应人工核查痛点。 |
| 报表台账 | 关键 | 做固定模板 | 支撑管理汇报和立项价值。 |
| 聊天查询 | 中等关键 | 限定意图 | 展示“智能助手”形态，但不能扩大成万能问答。 |
| 视觉识别模型训练 | 非首版关键 | 不做 | 业务资料已有视觉能力，demo 重点不是训练识别模型。 |
| YOLO / 多模态模型训练 | 非首版关键 | 不做 | 需要样本、标注、评测和算力，超出立项 demo。 |
| WeAct 真实推送 | 非首版关键 | 模拟 | 真实接口会引入联调、权限、网络和生产责任。 |
| PI / IMS 真实接入 | 非首版关键 | 模拟，预留适配器 | 接真系统是 C/D 档成本变量。 |
| 开放式 Agent | 非首版关键 | 不做 | 验收不可控，容易偏离巡检质量主题。 |
| 完整知识图谱 | 非首版关键 | 用最小规则表替代 | 正式项目再建设六大知识库和知识图谱。 |
| 品牌级视觉设计 | 视演示对象决定 | 默认做可信业务 UI | 如果用于高层答辩，可作为视觉增强项另估。 |

## 15. 不建议首版实现项

这些不是否定业务方想法，而是建议放入正式项目或增强版本。

| 不建议项 | 为什么不建议首版做 | 可替代展示 |
| --- | --- | --- |
| 全场站 / 阀室覆盖 | 范围过大，数据和规则无法在 demo 周期内确认 | 选 1 个典型站场故事，说明后续可复制。 |
| 50+ 视觉能力全部覆盖 | 不影响证明巡检质量分析闭环 | 选 1 类典型设备，其他作为扩展。 |
| 真实四源全量打通 | 接口、权限、网络、数据脱敏会显著拉长周期 | 用模拟四源数据，预留适配器。 |
| 本地部署大模型 | 需要 GPU、内网环境、运维、合规和调试 | 可选调用已批准模型 API，或先用模板解释。 |
| 训练时序深度模型 | 需要长期历史数据、故障标签和评测集 | 用轻量统计特征和规则实现趋势研判。 |
| 训练 YOLO / 多模态视觉模型 | 需要图片样本、标注、模型评测 | 使用已有视觉识别结果。 |
| 自动派单 / 自动审批 / 自动维保决策 | 安全生产责任边界不清 | demo 内模拟闭环和人工确认。 |
| 完整 PIPENET 知识图谱 | 是平台级能力，不是 demo 首版闭环必需 | 用设备台账、点位规则、隐患分级最小表。 |
| WeAgent / Coze 承载核心规则 | 规则调试、测试和验收不如后端清晰 | 可作为入口或包装，核心逻辑放后端。 |

关于是否基于现有示例项目开发：

| 方案 | 做法 | 优点 | 风险 | 建议 |
| --- | --- | --- | --- | --- |
| 直接复用完整平台 | 把现有平台整体改成 demo | 页面骨架可能较完整 | 容易继承无关复杂度，业务主线被平台功能干扰 | 不推荐默认承诺给业务。 |

| 抽取示例项目骨架 | 复用工作台布局、路由、表格、图表等基础能力，业务逻辑重写 | 兼顾效率和可控性 | 需要先评估示例项目质量和授权边界 | 推荐作为开发侧优先评估路径。 |

对业务方口径：

> 我们不会把开发底座本身作为业务价值卖点。业务方需要确认的是演示闭环、数据边界和功能范围；底座选择由开发侧根据工期、稳定性和可维护性评估。

## 17. 业务方必须确认的问题

### 17.1 目标和观众

1. 这次 demo 面向谁演示：领导、评委、业务部门、技术部门，还是未来使用人员？
2. 演示目标是看懂价值、验证可行性、争取立项，还是进入试点？
3. 现场演示形式是投屏讲解、答辩、录屏，还是让业务方自己点击体验？
4. 业务方最想打动谁：一线减负、管理提效、安全避险、集团复用，优先级怎么排？
5. 成功标准是“讲清楚价值”，还是“真实接入系统”，还是“能作为试点基础”？

### 17.2 业务规则

1. 设备健康等级怎么分：正常、关注、预警、严重，还是沿用已有隐患等级？
2. 哪类设备最适合做第一版故事：仪表、阀门、红外测温、指示灯、机柜设备？
3. 哪些参数能代表设备缓慢劣化：压力、温度、液位、读数偏差、状态变化？
4. 漏巡的业务定义是什么：未到点、超时、路径不完整、照片缺失，还是组合判断？
5. 虚假取证的业务证据是什么：照片重复、GPS 偏移、时间间隔异常、画面不符？
6. 填报不规范如何扣分：空值、模板化描述、描述与图片不一致、未填隐患？
7. 复合风险升级规则由谁拍板：生产部、安全部门、站场负责人，还是集团标准？
8. 风险升级后是否必须人工复核？

### 17.3 数据和接口

1. 第一版是否允许全程使用模拟数据？
2. 如果必须接真实系统，优先接哪一个：PI、机器视觉、IMS、WeAct、集团模型？
3. 是否能提供脱敏样例数据：时序、巡检记录、照片、隐患、人员、点位？
4. 视觉识别结果是否已有？字段是什么？是否包含置信度、读数、状态、图片路径？
5. PI 和视觉读数如何关联同一个设备或点位？
6. IMS 巡检记录是否有统一任务 ID、点位 ID、人员 ID 和时间戳？
7. WeAct 是否有测试环境、消息模板、回执状态和接口权限？
8. 数据冻结后是否允许继续新增样例？如果允许，是否作为变更处理？

### 17.4 模型和 AI

1. 是否必须展示 WeAgent / Coze / 集团大模型？
2. 是否允许模型接触人员姓名、轨迹、照片、隐患描述？
3. 模型输出是否只做解释和摘要，还是要参与评分和风险裁决？
4. 是否允许调用外部模型 API？如果不允许，内部模型接口谁提供？
5. 是否需要模型调用留痕、prompt 留痕、回答留痕？
6. 是否接受限定意图聊天，而不是开放式 Agent？

### 17.5 展示和验收

1. 必须做聊天窗口 + 极简页面双形态，还是二选一？
2. 是否需要大屏效果，还是普通 Web 工作台即可？
3. 是否必须贴近集团 / 湖南公司现有系统视觉风格？
4. 是否需要移动端？
5. 报表是页面展示即可，还是必须导出 PDF / Excel？
6. 演示脚本由谁确认？什么时候冻结？
7. 验收按固定脚本和固定数据，还是允许现场自由提问？
8. 如果现场临时新增问题、报表、规则，是否作为变更？

## 18. 开发前冻结项

在报价和排期前，建议冻结 6 件事：

| 冻结项 | 需要冻结什么 | 不冻结的后果 |
| --- | --- | --- |
| demo 目标 | 演示对象、演示目的、成功标准 | 页面和脚本容易做偏。 |
| demo 故事 | 站场、设备、人员、风险主线 | 功能范围会发散。 |
| 数据样例 | 设备数据、巡检数据、视觉结果、照片、报表字段 | 无法判断逻辑能否跑通。 |
| 规则口径 | 健康等级、扣分规则、复合风险升级条件 | 后端逻辑、报表和解释都会变。 |
| 演示形态 | A/B/C/D 档、页面、聊天、报表、闭环深度 | 报价和周期无法稳定。 |
| 验收口径 | 固定脚本、固定数据、固定报表、固定查询意图 | 容易把 demo 验收扩大成正式系统验收。 |

建议会议话术：

> 只要数据样例、规则口径、演示脚本、报表模板没有冻结，开发周期和报价都只能给区间，不能给固定总价。冻结后新增功能或新增接口，需要按变更处理。

会议收口时建议补一句：

> 今天需要明确三类责任人：规则由谁定，样例由谁给，验收由谁签。没有这三个责任人，demo 范围和验收口径就很难锁定。

## 19. 验收口径

推荐第一版验收口径：

> 在双方预先确认的数据样例、规则口径和演示脚本下，系统可稳定完成设备趋势研判、人员巡检质控、复合风险升级、风险解释、报表台账和限定意图查询，并且核心结论可追溯到来源数据和命中规则。

建议验收明细：

| 验收项 | 建议标准 |
| --- | --- |
| 数据 | 加载 1 套冻结 demo 数据集，包含设备、人员、巡检、视觉、风险样例。 |
| 设备研判 | 对 1 类设备输出趋势、异常段、健康等级、依据和维保建议。 |
| 人员质控 | 对 2-3 条规则输出命中结果、扣分项、证据定位。 |
| 复合风险 | 对 1 个典型故事展示风险升级原因和关联证据。 |
| 报表 | 输出 2-3 个固定模板，不临时新增字段和格式。 |
| 聊天 | 支持 3-5 个冻结意图，不承诺开放式自由问答。 |
| 闭环 | 展示 demo 内风险状态变化、模拟通知、整改确认和台账留痕。 |
| 可追溯 | 每条关键结论能回到来源记录、命中规则或证据图片。 |

不建议把申报材料中的收益口径直接作为 demo 验收：

| 申报口径 | demo 中的处理建议 |
| --- | --- |
| 人工核查降低 80% | 可作为预期价值展示，不作为第一版验收 KPI。 |
| 统计工时缩减 60% | 可通过报表自动生成展示趋势，不承诺真实统计。 |
| 单场站部署 1 天 | 可作为成熟产品推广目标，不作为首个 demo 承诺。 |
| 全场站 100% 覆盖 | 属于正式项目和推广阶段，不进入第一版。 |

## 20. 沟通话术

### 20.1 开场复述

> 我理解你们不是想再做一个普通巡检系统，而是想把已有的设备感知、人工巡检、消息和台账数据串起来，形成一个巡检质量智能分析助手。它要回答三个核心问题：设备有没有变坏，人员有没有认真巡，风险有没有形成闭环。

### 20.2 解释为什么先讲业务闭环

> 现在材料里有很多系统名词和技术名词，比如 PI、IMS、WeAct、WeAgent、知识图谱、多模态模型。但 demo 成功与否，首先取决于业务闭环是否讲清楚。我们先把“设备研判 + 人员评价 + 复合风险 + 报表台账”这条主线确认，再决定哪些真实做、哪些模拟、哪些留到正式项目。

### 20.3 解释为什么不做大而全

> 第一版如果一开始就覆盖所有场站、所有设备、所有接口、所有模型，范围会变成正式项目，周期和成本都不可控。立项 demo 更应该选一个典型故事，把业务价值讲透，后续再扩展。

### 20.4 解释为什么推荐 B 档

> 我建议第一版做可交互模拟 PoC。它不是静态页面，因为趋势分析、履职评分、复合风险和报表都是真实计算；但数据、消息和外部接口先模拟。这样既能证明价值，也不会被真实系统联调拖住。

### 20.5 解释为什么不训练 YOLO

> 你们材料里已经有机器视觉能力，首版 demo 的重点不是重新训练识别模型，而是说明视觉识别结果如何和 PI 时序、IMS 巡检记录一起形成巡检质量分析闭环。训练 YOLO 需要图片样本、标注、评测和算力，适合后续专项，不适合立项 demo 首版。

### 20.6 解释为什么不训练时序深度模型

> 设备趋势研判首版可以用轻量统计和业务规则真实计算，足够证明从瞬时告警升级到趋势分析。深度时序模型需要长期历史数据、故障标签和评测集，如果首版直接做，会把 demo 变成算法项目。

### 20.7 解释为什么大模型只做解释

> 在安全生产和人员考核场景里，第一版不建议让大模型直接裁决风险等级或扣分。更稳妥的方式是规则负责判定，模型负责解释、摘要和建议润色，这样责任边界清晰，也更容易验收。

### 20.8 推动业务拍板

> 今天我们最好确认 6 件事：演示对象、典型设备、巡检质控规则、复合风险故事、演示形态、验收口径。只要这 6 件事定下来，我就能把开发范围、周期和报价拆清楚。

## 21. 会议讨论清单

建议会议按下面顺序推进：

1. 先确认业务目标：这次是立项 demo、比赛答辩，还是试点 MVP。
2. 再确认核心故事：选哪个站场、哪类设备、哪类巡检问题。
3. 再确认业务规则：设备健康等级、人员扣分、复合风险升级。
4. 再确认演示形态：A/B/C/D 选哪档。
5. 再确认真实性边界：哪些是模拟数据、哪些是真实计算、哪些是 AI 增强。
6. 再确认页面和报表：页面数量、聊天意图、报表模板。
7. 最后确认冻结项：数据、规则、脚本、报表、验收。

会议结束时应形成的结论：

| 结论项 | 会议后应明确 |
| --- | --- |
| demo 档位 | A / B / C / D。 |
| 第一版故事 | 站场、设备、人员问题、复合风险主线。 |
| 数据方式 | 全模拟、接 1 个真实接口，还是真实部署。 |
| 功能范围 | 必做、可选、后续。 |
| 展示形态 | 页面、聊天、报表、闭环状态。 |
| 模型边界 | 是否接模型，接什么模型，模型做什么。 |
| 验收方式 | 固定数据、固定规则、固定脚本、固定报表。 |
| 业务负责人 | 谁拍板规则、数据、脚本和验收。 |

## 22. 后续正式项目路线

第一版 demo 不等于正式项目，但要能自然引出正式项目。

建议路线：

```text
阶段 1：业务架构与 demo 范围确认
  梳理业务闭环
  冻结 demo 故事
  冻结数据和规则
  确认 A/B/C/D 档位

阶段 2：立项 demo / PoC
  模拟数据
  真实规则和轻量算法
  复合风险闭环
  固定报表和限定聊天

阶段 3：试点 MVP
  接入 1 个真实站场或 1 个真实系统
  固化业务规则
  完善权限、审计、部署和联调
  形成试点验收

阶段 4：正式项目
  四源真实打通
  多设备、多站场、多规则
  WeAct / 工单 / 审批闭环
  知识库和规则管理
  模型评测与迭代

阶段 5：推广复用
  标准化 Skill / 工作流 / 提示词 / 评测集
  场站复制模板
  运维手册
  集团或区域级推广
```

对业务方建议的结束话术：

> 第一版 demo 我建议先证明最核心的一条闭环：设备趋势异常、人员巡检质量问题、复合风险升级和报表台账。只要这条跑通，后续接 PI、IMS、WeAct、集团模型、知识库和多站点复制，都有明确的扩展路径。这样立项有说服力，开发范围也可控。

## 23. 当前推荐结论

建议你在第一次需求讨论会中给出明确推荐，而不是只罗列选项：

> 我建议第一版做 B 档：可交互模拟 PoC。

推荐组合如下：

| 维度 | 推荐结论 |
| --- | --- |
| demo 目标 | 证明“设备研判 + 人员评价 + 复合风险 + 报表台账”的业务闭环。 |
| 演示范围 | 1 个站场 / 区域、1 类设备、2-3 条人员质控规则、1 条复合风险故事。 |
| 数据方式 | 模拟 PI、IMS、视觉结果、WeAct 状态。 |
| 真实能力 | 真实轻量时序计算、真实履职评分、真实复合风险规则、真实报表生成。 |
| AI 能力 | 可选模型解释和摘要，不做风险裁决。 |
| 页面形态 | 首页、设备详情、人员履职、复合风险、报表台账、聊天入口。 |
| 不做事项 | 不训练 YOLO、不训练深度时序模型、不做真实四源全量接入、不做开放式 Agent、不做完整知识图谱。 |
| 后续扩展 | 立项后按 C/D 档接真实系统、真实闭环、知识库、模型评测和多站点复制。 |

这份推荐的核心逻辑是：

```text
立项 demo 要先打动业务和评审
  所以必须让分析闭环真实跑起来

立项 demo 又不能变成正式项目
  所以数据、接口、通知、模型训练必须控制边界

第一版最优解
  模拟数据 + 真实规则 / 轻量算法 + 可交互页面 + 固定报表 + 限定聊天
```
