# 巡检质量智能分析助手 demo 立项沟通方案

> 归档说明：本文保留为历史立项沟通参考，不再作为当前维护入口。当前对外方案见 [../巡检质量智能分析助手-demo-AI赋能演示定稿方案.md](../巡检质量智能分析助手-demo-AI赋能演示定稿方案.md)，当前技术方案见 [../巡检质量智能分析助手-demo-技术实施定版方案.md](../巡检质量智能分析助手-demo-技术实施定版方案.md)。

本文用于把业务方提供的申报资料转化为 demo 洽谈口径，重点回答 demo 目标、第一版范围、功能取舍、资源需求、待确认问题和验收边界。

## 0. 会议速览

先拿下面 6 个问题和业务方确认，确认后再报价：

| 必须确认 | 推荐立场 | 如果业务方不同意 |
| --- | --- | --- |
| 这次是立项 PoC 还是试点 MVP | 推荐先做立项 PoC | 如果按试点 MVP，要单独评估真实接口、部署、联调和验收。 |
| 是否允许模拟数据完整演示 | 推荐允许 | 如果必须接真实系统，demo 不应按模拟 PoC 报价。 |
| 闭环做到哪一层 | 推荐做模拟闭环 | 如果要真实 WeAct、工单、审批联动，需要另列范围。 |
| 第一版演示哪个典型业务故事 | 推荐只选 1 个站场 / 1 类设备 / 2-3 类巡检规则 | 如果要多站点、多设备、多规则，周期和报价按扩展项计算。 |
| 数据、规则、脚本谁拍板 | 推荐指定唯一业务确认人并设置冻结时间 | 未冻结前不要承诺最终交付时间。 |
| 验收按什么通过 | 推荐按已冻结样例、固定脚本、固定报表模板验收 | 不建议按 80%、60%+、50%+ 等申报收益指标验收。 |

我的推荐版本：做 `B 档：可交互模拟 PoC`。它用模拟数据跑通设备趋势研判、人员巡检质控、复合风险升级和报表台账，足够支撑立项沟通，同时不会把真实系统集成和正式项目责任提前背进 demo。

## 1. 先判断这件事

业务方资料里同时包含三层目标，必须在报价和排期前拆开：

| 层级 | 目标 | 适合当前 demo 吗 | 说明 |
| --- | --- | --- | --- |
| 大赛 / 立项演示 PoC | 用模拟数据完整演示“设备研判 + 人员评价 + 复合风险 + 报表台账”闭环 | 适合 | 申报书明确提到“轻量化 PoC 原型”“通用模拟巡检数据集”“无需依赖外部单位场站资源即可演示”。 |
| 湖南公司试点 MVP | 对接现有智能巡检底座、IMS 等真实系统，在一个试点场站跑真实业务 | 可作为下一阶段 | 需要业务接口、数据权限、现场规则、部署环境和验收口径，不能按 demo 成本估算。 |
| 正式项目 / 集团推广 | 四数据源打通、六大知识库、按月模型迭代、全域复制、场站阀室 100% 覆盖 | 不适合作为第一版 | 这是远期产品和推广目标，不应进入 demo 首版验收。 |

我的建议：第一版先做“可稳定演示的业务闭环 PoC”，不要一开始承诺真实系统集成、全量知识图谱、自动模型迭代、全场站覆盖。demo 的价值在于帮助业务方立项和统一认知，不是替代正式项目交付。

## 2. demo 的核心目标

demo 不是做一个普通 AI 聊天页面，而是证明“巡检数据可以从记录资产变成分析资产”。

第一版需要证明四件事：

1. 设备侧能从瞬时告警升级为长期趋势研判。
2. 人员侧能从人工核查巡检资料升级为 AI 自动质控。
3. 设备异常和人员漏检能被关联为复合风险。
4. 系统能输出可追溯的风险、建议、台账和报表，用于管理决策。

推荐的 demo 叙事主线：

```text
模拟数据进入
  -> 设备趋势异常识别
  -> 人员巡检质量判定
  -> 设备异常 + 人员漏检叠加升级
  -> 输出风险预警、维保建议、履职台账、报表
  -> 通过聊天窗口或极简页面查询与展示
```

## 3. 第一版推荐范围

### 3.1 推荐做法

第一版建议定位为“可交互业务演示 demo”，而不是纯 PPT 原型，也不是完整生产系统。

推荐形态：

| 模块 | 第一版建议 | 原因 |
| --- | --- | --- |
| 数据 | 使用业务方确认的模拟数据集，必要时支持离线文件导入 | 申报资料本身支持 PoC 用模拟数据独立演示，这是控制工期和风险的关键。 |
| 设备研判 | 选 1 类典型设备，展示历史趋势、异常识别、健康等级、维保建议 | 设备侧是“从告警到研判”的核心卖点，不需要一开始覆盖 50+ 视觉能力。 |
| 人员质控 | 展示漏巡、虚假取证、填报不规范 2-3 类规则 | 人员履职评价是区别于单纯机器视觉巡检的核心能力。 |
| 复合风险 | 展示“设备持续异常 + 人员多次漏检”自动升级预警 | 这是方案最有说服力的差异化点，必须保留。 |
| 报表台账 | 生成设备趋势报表、人员履职台账、综合风险清单中的至少 2 类 | 业务方需要看到管理价值和可审计追溯。 |
| 交互 | “聊天窗口 + 极简页面”二选一或简单联动 | 演示重点是业务闭环，视觉和交互应服务展示，不宜变成大型后台。 |
| 闭环 | 展示风险记录、处置建议、状态变化，不直接做真实派单 | 自动派单、审批、工单闭环属于下一阶段范围。 |

### 3.2 必须先拍板的闭环深度

闭环深度是 demo 成本分界线，不能含糊写成“闭环处置”。

| 选项 | 交付含义 | 我的建议 |
| --- | --- | --- |
| 模拟闭环 | demo 内展示风险产生、建议生成、状态变化、台账记录，不调用真实消息、工单、审批系统 | 第一版推荐。 |
| 半真实闭环 | 只接 1 个真实通知或接口，其余流程模拟 | 需要业务方提前提供接口、账号、测试环境和联调窗口。 |
| 真实闭环 | 接入 WeAct、工单、审批、整改追踪等真实生产链路 | 不建议纳入立项 demo，应作为试点 MVP 或正式项目范围。 |

建议会议上直接让业务方二选一：第一版是“模拟闭环演示”，还是“真实系统联动”。如果选择真实联动，报价和周期必须重算。

### 3.3 建议第一版演示脚本

建议把 demo 控制在一个典型场景里，例如“某站场某设备区发现设备劣化，同时人员多次漏巡，系统自动识别并升级风险”。

演示步骤：

1. 进入首页，展示今日巡检概览：设备异常数、人员巡检得分、待处置风险。
2. 打开设备详情，看到某仪表或阀门的历史趋势异常，系统给出健康等级和维保建议。
3. 打开人员巡检记录，看到打卡、照片、填报记录，系统标出漏巡或虚假取证证据。
4. 打开复合风险页，系统解释为什么从普通异常升级为高风险。
5. 用自然语言查询：“本周哪些设备存在高风险？”或“张三本周巡检质量如何？”
6. 导出或展示报表：设备趋势、人员履职、风险闭环台账。

### 3.4 第一版验收建议

建议验收口径写成：

> 在双方预先确认的数据样例、规则口径和展示脚本下，系统可稳定完成设备趋势研判、人员巡检质控、复合风险升级和标准报表输出，并且所有结论可追溯。

为了避免“稳定完成”“可追溯”被扩大解释，建议在合同或报价单里把验收锁成以下颗粒度：

| 验收项 | 建议标准 |
| --- | --- |
| 数据 | 加载 1 套双方冻结的 demo 数据集；数据范围、字段、样例数量在开发前确认。 |
| 设备研判 | 对 1 类典型设备、至少 1 个正常样例和 1 个异常样例，输出异常识别结果、健康等级、依据说明、维保建议。 |
| 人员质控 | 对 2-3 类已冻结巡检规则，输出命中结果、扣分项、证据定位。 |
| 复合风险 | 对 1 个“设备持续异常 + 人员漏检”样例，展示风险升级原因和关联证据。 |
| 报表 | 固定 2-3 个报表模板，例如设备趋势报表、人员履职台账、综合风险清单；不临时新增模板。 |
| 查询 | 固定 3-5 个演示查询意图，例如“本周高风险设备”“某人员巡检质量”“某设备维保建议”；开放式问答另算。 |
| 追溯 | 每条结论至少回溯到来源记录、命中规则、关键证据三类信息中的 2 类；缺失数据必须明确提示。 |
| 演示稳定性 | 按冻结脚本完整演示 1 次，不依赖现场临时补数据、临时改规则或临时改页面。 |

验收前应冻结三件事：

1. `demo 数据集`：样例数量、字段、异常样例、正常样例。
2. `规则口径`：设备健康等级、巡检扣分项、复合风险升级条件。
3. `演示脚本`：页面路径、查询意图、报表模板、讲解顺序。

冻结后新增数据、新增规则、新增页面、新增接口、新增报表模板，都应视为变更范围。

## 4. 功能取舍建议

### 4.1 必须保留

| 功能 | 为什么必须保留 |
| --- | --- |
| 设备时序研判 | 解决“机器视觉只做瞬时告警”的痛点，是设备侧核心价值。 |
| 人员履职评价 | 解决“人工核查轨迹、照片、文字记录”的痛点，是人员侧核心价值。 |
| 复合风险升级 | 解决“设备数据和人员数据割裂”的痛点，是本方案最强差异化。 |
| 报表 / 台账 | 业务方要用于管理、汇报、立项，必须能看到可落地的产出物。 |
| 可追溯证据 | 设备异常、扣分、风险升级都要能回到来源数据或规则，否则验收风险很大。 |

### 4.2 可以第一版简化

| 功能 | 简化方式 |
| --- | --- |
| 四大真实数据源接入 | 先用模拟数据或离线文件；真实 `PI / 机器视觉 / IMS / WeAct` 接口作为下一阶段。 |
| 50+ 机器视觉能力 | 第一版只选 1-2 类典型设备或状态，其他用后续扩展说明。 |
| 六大知识库 | 先做首个演示场景的最小规则集和样例库，不做完整知识图谱。 |
| 按月模型迭代 | demo 展示“样本可沉淀、台账可追溯”，不承诺自动迭代闭环。 |
| 多角色权限 | 第一版只区分一线运维和管理 / 督查两个视角，避免完整权限系统。 |
| WeAct 消息闭环 | 先做模拟通知和状态流转，真实消息推送另算。 |
| 视觉设计 | 做业务可信、清晰、适合汇报的界面即可，不做完整品牌级 UI 设计。 |

### 4.3 不建议第一版实现

| 不建议项 | 原因 |
| --- | --- |
| 全国场站 / 阀室 100% 覆盖 | 属于正式项目和推广目标，不是 demo 验收范围。 |
| 单场站 1 天部署承诺 | 这是成熟产品复制阶段的指标，首个 demo 不应作为合同 KPI。 |
| 真实四源全量打通 | 数据权限、接口规范、网络环境、部署审批都会显著拉长周期。 |
| RPA 多系统采集 + 数据湖 + BI 趋势平台 | PPT 中出现过，但这会扩张成相邻数据平台项目。 |
| PPS / 生产日报 / 审批分发 / 文件审阅 | 这些已经超出“巡检质量智能分析助手”的最小闭环。 |
| 自动派单、自动审批、自动维保决策 | 首版应定位为辅助决策，避免安全和责任边界不清。 |
| 多模型混合底座适配 | 先锁定一个可用技术底座；多模型适配会增加部署、合规和调试成本。 |

## 5. 需要和业务方确认的问题

### 5.1 目标和验收

1. 这次要做的是“大赛 / 立项演示 PoC”，还是“湖南公司试点 MVP”？
2. demo 的观众是谁：领导、评委、业务部门、技术部门，还是未来使用人员？
3. 现场演示形式是什么：会议投屏、答辩、客户试用、录屏，还是现场可点击体验？
4. demo 成功的标准是什么：看懂价值、跑通流程、验证技术可行性，还是能进入试点？
5. 资料里的 `80% 人工核查降低`、`60%+ 统计工时缩减`、`50%+ 人力投入减少` 是否只是申报口径，还是要写入验收指标？
6. 验收是否同意按冻结数据集、冻结规则、冻结脚本和固定报表模板执行？
7. 业务方是否接受“模拟闭环”作为第一版闭环深度？

### 5.2 数据和接口

1. demo 是否允许全程使用模拟数据？
2. 如果要接真实数据，能提供哪些接口、字段、样例、权限和测试环境？
3. 是否能提供脱敏的巡检轨迹、打卡时间、照片、填报记录、设备时序数据？
4. 机器视觉识别结果是已有系统输出，还是需要 demo 自己识别图片？
5. 设备侧需要多长周期历史数据：7 天、30 天、90 天，还是只需演示样例？
6. 数据缺失、异常、冲突时，业务希望系统如何呈现？
7. demo 数据集由谁提供，什么时候冻结？
8. 数据冻结后是否允许新增样例？如果允许，是否作为变更处理？

### 5.3 规则和算法

1. 漏巡的定义是什么：未到点、超时、路径不完整、照片缺失，还是多条件组合？
2. 虚假取证如何判断：图片重复、位置不符、时间异常、画面不符，还是人工标注样例？
3. 填报不规范有哪些扣分项和评分公式？
4. 设备健康等级如何划分：正常、关注、预警、严重，还是其他业务等级？
5. 维保建议由业务规则生成，还是需要大模型生成自然语言建议？
6. 复合风险升级规则由谁拍板，是否需要可解释文本？
7. 规则口径由谁最终确认，什么时候冻结？
8. 冻结后新增扣分项、设备等级或风险升级条件，是否作为变更处理？

### 5.4 界面和演示形式

1. 必须做“聊天窗口 + 极简页面”双形态，还是二选一即可？
2. 是否需要大屏效果，还是普通 Web 管理界面即可？
3. 是否需要贴近集团 / 湖南公司现有系统视觉风格？
4. 是否需要移动端，还是桌面投屏优先？
5. 是否需要导出 PDF / Excel，还是页面展示即可？
6. 是否需要演示数据录入后台，还是开发侧预置数据即可？
7. 演示脚本由谁最终确认，什么时候冻结？
8. 现场是否允许临时自由提问？如果允许，是否接受只覆盖预置查询意图？

### 5.5 部署和合规

1. demo 部署在哪里：本地电脑、客户内网、服务器、集团平台环境？
2. 是否必须使用 WeAgent、Coze、IMS、集团大模型等内部平台？
3. 是否允许外部开发环境先做演示版，再迁移到内部环境？
4. 是否有数据安全、脱敏、网络隔离、账号权限要求？
5. 是否需要源码交付、部署文档、操作手册、培训？

## 6. 资源需求

### 6.1 业务方需要提供

| 资源 | 用途 | 没有会怎样 |
| --- | --- | --- |
| demo 目标和观众 | 决定演示深度和界面形态 | 容易做偏，影响报价和验收。 |
| 典型站场 / 设备 / 巡检场景 | 聚焦第一版样例 | 范围会发散到全场景。 |
| 样例数据或模拟数据口径 | 支撑设备趋势、人员质控、报表 | 只能做静态页面，无法证明闭环。 |
| 巡检规则和评分口径 | 支撑人员履职评价 | 容易出现验收争议。 |
| 设备健康等级规则 | 支撑设备研判 | 输出结果缺少业务可信度。 |
| 演示脚本确认人 | 锁定 demo 现场路径 | 现场容易临时改需求。 |
| 范围冻结确认人 | 冻结数据、规则、脚本、报表模板 | 周期和报价无法稳定。 |
| 视觉风格参考 | 控制 UI 工作量 | 视觉投入无法估算。 |
| 部署环境要求 | 决定技术实现方式 | 后期迁移成本可能很高。 |

### 6.2 开发侧需要准备

| 资源 | 说明 |
| --- | --- |
| 产品 / 需求梳理 | 把资料转成演示流程、页面清单、验收口径。 |
| 前端实现 | 首页概览、设备详情、人员质控、复合风险、报表、对话入口等。 |
| 数据建模 | 设计模拟数据结构，覆盖设备、人员、巡检、规则、风险、报表。 |
| 分析逻辑 | 实现趋势识别、规则判定、评分、风险升级、解释生成。 |
| AI / 大模型集成 | 如需要自然语言查询或建议生成，需要明确模型来源和调用方式。 |
| 演示脚本和测试 | 保证现场按固定路径稳定展示。 |
| 文档 | 交付说明、演示说明、范围边界、后续正式项目建议。 |

## 7. 报价和周期的关键变量

不要在下面变量未确认前给固定总价：

| 变量 | 低成本口径 | 高成本口径 |
| --- | --- | --- |
| 数据来源 | 模拟数据 / 离线文件 | 真实接口、跨网、权限审批、数据清洗 |
| 视觉能力 | 复用已有识别结果 | 新增图像识别、模型调优、样本标注 |
| AI 能力 | 规则 + 固定模板 | 大模型问答、RAG、工具调用、私有化部署 |
| 页面数量 | 3-5 个核心页面 | 多角色工作台、大屏、移动端、后台管理 |
| 报表 | 页面展示或简单导出 | PDF/Excel 模板、审计台账、批量导出 |
| 闭环 | 模拟处置状态 | WeAct、工单、审批、整改追踪真实联动 |
| 部署 | 本地或单服务器演示 | 客户内网、集团平台、网络隔离、合规审查 |
| 视觉设计 | 清晰可演示 | 品牌级设计、动效、大屏、汇报视觉包装 |

建议报价拆成三档，方便和业务方谈：

| 档位 | 定位 | 适用情况 |
| --- | --- | --- |
| A 档：汇报型可点击原型 | 重点展示界面和流程，数据多为静态或半静态 | 预算低、时间紧、只为立项讲清楚。 |
| B 档：可交互模拟 PoC | 模拟数据驱动完整闭环，有规则、有报表、有演示脚本 | 最推荐，能证明业务价值，又能控制风险。 |
| C 档：半真实集成 demo | 接 1 个真实系统或真实数据源，其余模拟 | 适合业务方已有接口和环境，且愿意承担更长周期。 |

我的建议是优先谈 B 档。如果业务方坚持真实系统对接，则把真实接口、部署环境、联调、数据治理作为单独报价项，不要混进 demo 基础报价。

## 8. 视觉是否要做

建议做“可信的业务演示视觉”，不要做“正式产品级视觉系统”。

第一版视觉应满足：

- 投屏时看得清。
- 首页能一眼看到设备风险、人员履职、复合风险、待处置事项。
- 详情页能解释结论来源。
- 报表页能支撑管理汇报。
- 不追求复杂动效、完整设计规范、全角色工作台。

如果业务方明确要用于高层汇报、比赛答辩或招商展示，可以增加视觉包装；如果只是内部技术验证，视觉投入应压缩，把时间放在业务闭环和可追溯证据上。

## 9. 正式项目后续路线

如果 demo 立项成功，正式项目可以拆成三步，不建议一次性全做：

| 阶段 | 目标 | 范围 |
| --- | --- | --- |
| 试点 MVP | 在一个场站或一个业务区域接入真实数据 | 真实数据接入、规则固化、人员评价、设备研判、报表输出。 |
| 生产试运行 | 在湖南公司更多场景验证稳定性 | 权限、日志、审计、消息、工单、运维、性能、容错。 |
| 复制推广 | 标准化为可复用 AI 资产 | WeAgent Skill、知识库、提示词、工作流、评测集、部署手册。 |

## 10. 我建议你和业务方这样谈

第一轮访谈不要先谈“全部功能”，先锁定四个边界：

1. 这是立项 PoC 还是试点 MVP？
2. 是否允许模拟数据完整演示？
3. 第一版只演示哪一个典型业务故事？
4. 验收是“演示跑通”还是“真实业务可用”？

可以直接使用下面这段沟通口径：

> 我建议第一版先做可交互模拟 PoC，用双方确认的数据样例跑通设备研判、人员质控、复合风险升级和报表台账。这样可以把立项最需要看的业务价值讲清楚，也能控制开发周期和报价。真实系统对接、全量知识库、模型迭代、消息 / 工单闭环和多站点复制，建议作为立项后的试点或正式项目范围单独评估。

## 11. 资料中的口径差异和风险点

| 风险点 | 说明 | 建议 |
| --- | --- | --- |
| 团队名称不一致 | 申报书为“管网巡智先锋队”，PPT 中出现“管网弈智先锋队”。 | 让业务方统一对外材料口径。 |
| 赛道信息可能混杂 | 报名表中出现数智员工、桌面办公助手、深度研究等赛道信息。 | 确认最终申报 / 演示定位。 |
| PPT 范围明显扩张 | PPT 出现生产日报、PPS、审批分发、RPA、数据湖、BI 等内容。 | 明确这些是否属于本 demo；默认不纳入第一版。 |
| 量化收益不适合直接验收 | 80%、60%+、50%+ 更像申报价值口径。 | demo 验收按样例流程和功能结果，不按长期经营指标。 |
| “自动决策”责任边界不清 | 巡检和维保涉及安全生产，不宜首版自动执行。 | 第一版定位为辅助决策和建议输出。 |
